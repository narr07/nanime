A small deck sits with the next two cards peeking out behind the front
one. Drag the front card sideways and let go: past a distance it flies off
in that direction and the next card takes its place, short of that
distance it springs back to center.

## What's happening

The front card tilts as it's dragged, more tilt the further it moves.
Release it near the center and it snaps back straight. Release it far
enough to either side and it keeps going, sliding off the edge and fading
out, and the card that was peeking behind it becomes the new front card.

## How it's built

[`useDraggable`](/composables/use-draggable) moves the front card handle
and reports its position through `onGrab` and `onUpdate`. `y: false` locks
the drag to the horizontal axis. The handle's own position is recorded
once in `onGrab` rather than assumed to start at `0`, because `x` reports
the element's absolute position, not how far the current drag has moved
it, so a card released off-center on the last drag would otherwise read
as further from the threshold than it visually is.

The tilt while dragging, and the slide-and-fade on dismiss, both animate a
child element rather than the handle `useDraggable` moves. `useDraggable`
writes the handle's `transform` on every frame it's active, so setting
`transform` on that same element from anywhere else means the two write
to the same property and one wins each frame, not both. Reading the drag
delta in `onUpdate` and writing it to a plain `tilt` ref, then applying it
as `rotate` on the inner `.swipe-card`, sidesteps that entirely.

The dismiss animation uses [`useAnimatable`](/composables/use-animatable)
rather than a fresh `useAnimate` call fired from the release handler. Its
target is a plain `reactive({ x: 0, rotate: 0, opacity: 1 })` object, not
the card, so the values it tweens are just numbers a computed style reads
from. `useAnimatable` is set up once, at the top level, the same as every
composable on this page. Calling a composable itself from inside an event
handler after setup has already run is what to avoid, calling the plain
setter functions it returns from an event handler is what it's for, and
`exitTo.x?.(...)` is exactly that.

Past the threshold, `onRelease` calls `draggable.stop()`, which freezes
the handle exactly where the drag left it, and starts the exit tween on
the child. Short of the threshold, `onRelease` does nothing: `snap: [0]`
and `releaseEase: spring(...)` already carry the handle back to center on
their own. Once the exit tween's duration has passed, a `setTimeout`
advances to the next card, resets the exit values and the tilt, and calls
`draggable.reset()` to put the handle back at the origin for the next
drag.

## Building it yourself

1. Layer the deck: one or two static "peek" cards positioned behind, and a
   draggable handle in front holding the active card.
2. Call `useDraggable(handle, { y: false, snap: [0], releaseEase:
   spring({...}), onGrab, onUpdate, onRelease })`. Record the handle's `x`
   in `onGrab` and subtract it from `x` in later callbacks, `x` is an
   absolute position, not a delta.
3. In `onUpdate`, write the drag delta to a plain ref and apply it as
   `rotate` on a child element inside the handle, never on the handle
   itself.
4. Set up `useAnimatable` once on a plain reactive object
   (`{ x, rotate, opacity }`), not on the card, with the duration and ease
   for the dismiss animation.
5. In `onRelease`, if the delta passes the threshold, call
   `draggable.stop()` and call the animatable's setters to slide and fade
   the child element out.
6. After the dismiss duration, advance to the next card, reset the plain
   object's values directly (no tween needed, nothing is visible yet), and
   call `draggable.reset()`.
